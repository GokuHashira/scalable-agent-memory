# Workstream V: data, evaluation, and findings

Project 27 (CMSC 848N): large memory with bounded retrieval and maintenance cost.
This branch (`vgdev`) adds the data and evaluation side of the project: dataset adapters, the reader and
judge harness, metrics and statistics, the synthetic update workload, and the experiments below. All numbers
come from runs on UMD Zaratan. Run outputs (`runs/`, `data/`) are regenerated by the scripts named in each
section and are not committed.

## 2. Methods

### 2.1 Data
- **LongMemEval_S** (authors' cleaned release, `xiaowu0162/longmemeval-cleaned`).
  - One history per question.
  - One note per turn (`note_id = <qid>:<session>:<turn>`, timestamp = session date), plus one session-parent
    note per session.
  - Gold labels: `gold_session_ids` = `answer_session_ids`; `gold_note_ids` = turns marked `has_answer`.
  - **Split:** 100 dev / 400 test, stratified by question type × abstention, seed 0. Anything tuned (prompts,
    judge choice) was chosen on dev only. Every headline number is on test unless marked dev.
  - **Leakage guards:** raw session ids name evidence sessions `answer_…`, so session ids are replaced by a
    salted hash. `has_answer` never enters note metadata.
  - **Size:** 500 questions, 270,617 notes (246,750 turns), about 103K tokens per history.
  - The original (uncleaned) release has the same 500 questions and identical gold labels, but contains 1,230
    empty sessions; the cleaned release is used.
- **LongMemEval_Oracle:** the same questions with evidence sessions only.
- **LongMemEval_M:** the same questions with ~1.02M tokens per history; 2.68M notes.
- **LongMemEval-V2 Small, text-only:**
  - 422 of 451 questions (the 29 screenshot questions are dropped).
  - The two shared 100-trajectory haystacks (55M tokens) become 90,627 notes: one note per agent step, plus the
    page accessibility tree in 512-token chunks.

### 2.2 Synthetic workload (`src/mem27/data/synth.py`)
- **Entities:** persons, projects and orgs with invented names (so the reader cannot answer from
  pretraining), each with attribute timelines.
- **Value changes** come in two kinds:
  - *supersede*: the fact changed;
  - *correct*: an earlier statement was wrong.

  Each change is either *explicit* ("changed from A to B", with a `supersedes` pointer) or *implicit* (the new
  value is restated with no reference to the old one).
- **Distractor tiers:** filler, near-duplicate "twin" entities, same entity with another attribute,
  superseded versions, and a meeting-event graph.
- **Queries:** six types (exact lookup, semantic recall, latest value, point-in-time with `as_of_time`,
  what-changed, multi-hop).
- **Streams:** a base corpus plus an update stream in timestamp order. Mid-stream questions shift their query
  mix at the midpoint.
- **Properties:**
  - Byte-identical output for a fixed seed.
  - Generated at 10K / 50K / 100K notes (seeds 0–2) and 1M notes (seed 0; 117 s, 2.5 GB).
  - Update-rate sweep: none / low / medium / high.

### 2.3 Reader, judge, and serving
- **Reader:** Qwen3-8B, non-thinking, greedy.
  - **Pinned prompt:** chain-of-note. The reader extracts the relevant facts with their session dates, then
    reasons, then ends with "Final answer:". It was chosen on dev (§3.3).
  - **Bundle rendering:** passages are grouped by session, sessions sorted by date with the date shown, turns
    in order.
- **Official judge:** gpt-oss-20b (reasoning effort low), using the LongMemEval judge prompts verbatim.
- **Second judge:** Qwen3-32B, reported alongside.
- **Serving:**
  - GPU queues were saturated, so most runs used llama.cpp on CPU nodes: Qwen3-8B Q8_0 and gpt-oss-20b MXFP4,
    natively built, two servers per node pinned per socket.
  - Some runs used vLLM bf16 on an H100.
  - A backend check on 4×121 identical prompts found 86–92% identical verdicts and no significant accuracy
    difference (§3.9).
- **Open-weight models only.** No paid APIs.

### 2.4 Metrics and statistics
- **Evidence metrics:**
  - Gold-session and gold-turn recall@k: k counts notes in rank order, and a session-parent note covers its
    turns.
  - Context precision (count- and token-weighted), nDCG@10 and MRR at session level.
  - Tokens (cl100k) and p50 / p95 latency per stage.
- **Accuracy:**
  - Judged correctness: overall, task-averaged, and abstention accuracy.
  - Accuracy conditioned on full gold coverage of the bundle, which separates retrieval failures from reading
    failures.
- **Freshness@k:** for an updated fact, the latest version is in the top k *and* ranks above every superseded
  version.
- **Stale-served rate:** the answer states a superseded value and not the current one. For synthetic data
  this is an exact string match; for LongMemEval knowledge-update questions it is an LLM stale judge.
- **Maintenance work per update:** aggregated from insert traces (embedding, BM25, ANN, summary and link
  time, plus summary tokens).
- **Statistics:**
  - Paired bootstrap: 10,000 resamples, seed 0, percentile 95% CIs, overall and per type.
  - Verdicts at the pre-registered ±2-point margin.
  - Power: the paired-difference SD, MDE at 80% power, and the n needed for ±2-point equivalence.
- **Reference retrievers:** BM25, dense (bge-base-en-v1.5) and hybrid (RRF, k = 60), turn level, packed
  under the shared budget (2,048 tokens, 20 notes). They validate the harness and are not the project's
  retrieval systems.

## 3. Findings

### 3.1 LongMemEval_S validity audit (`scripts/audit_lme_leakage.py`)
- **Session-id leak.** Raw ids identify every evidence session (`answer_…`). Pipelines that index raw ids can
  look better than they are; our conversion hashes them.
- **Most of each haystack is easy to dismiss.** Per history there are 47.7 sessions on average:
  - 24.4 real chats (12.4 ShareGPT + 12.0 UltraChat),
  - 21.5 simulated user sessions written for *other* questions,
  - 1.9 evidence sessions.
- **A detector that never sees the question** (TF-IDF + logistic regression, 5-fold CV grouped by history)
  separates evidence sessions from real chats almost perfectly but cannot pick them out of the simulated ones:

  | evidence vs | AUC |
  |---|---|
  | ShareGPT | 0.964 |
  | UltraChat | 0.960 |
  | simulated sessions | 0.575 |

  Ranking by this prior alone reaches session recall@10 of 0.461 (random 0.211). The effective haystack is
  about 23 simulated sessions, not 48. The artifact adds under 1 point when fused into retrieval.
- **Errors fall in the hard tier.** Of the non-gold sessions in the top 10, 64–71% are simulated sessions.
- **Label gaps.**
  - About 3% of gold sessions have no turn marked `has_answer`, which caps turn-based session recall at 0.966.
  - One answer turn is 12K tokens long, so the 2,048-token cap can cut real evidence.

### 3.2 Retrieval reference numbers (test, 2,048-token budget)
| retriever | session recall@5 | session recall@20 | turn recall@20 | precision | p95 latency |
|---|---|---|---|---|---|
| BM25 | 0.858 | 0.921 | 0.787 | 0.619 | 2.3 ms |
| dense (bge-base) | 0.875 | 0.940 | 0.845 | 0.735 | 56 ms (CPU query embedding) |
| hybrid (RRF) | 0.901 | 0.943 | 0.843 | 0.738 | 59 ms |

- A 2,048-token bundle holds about 10 turns. The token cap binds before `max_results`: 8–12% of answer turns
  rank in the top 20 but are cut by the cap.

### 3.3 Reader-wrapper choice (dev, 100 questions)
| bundle | concise | official LongMemEval prompt | **chain-of-note (pinned)** | CoN, rank order | CoN + date hints |
|---|---|---|---|---|---|
| gold sessions | 64.0 | 68.0 | **78.0** | 74.0 | 74.0 |
| BM25 | 52.0 | 59.0 | **64.0** | 62.0 | 65.0 |

(Qwen3-32B judge. Re-scored with gpt-oss-20b, chain-of-note still wins: 81.0 and 63.0.)
- **Chain-of-note gains 5–10 points from the reader wrapper alone.**
- **Chronological session grouping beats retrieval-rank order.**
- **Date hints** ("N days before the current date") do not help; temporal accuracy dips (0.69 → 0.62).
- **More context around the evidence hurts.** Gold answer turns alone (≈ 380 tokens) score higher than the
  same turns plus their full sessions.

### 3.4 Held-out results with the pinned reader (test, 400 questions)
Official judge gpt-oss-20b, Qwen3-32B in brackets. Δ is paired against hybrid.

| bundle (2,048-token cap unless noted) | accuracy [Qwen] | Δ vs hybrid [95% CI] |
|---|---|---|
| gold answer turns only (≈ 370 tokens) | 83.8 [84.8] | +12.8 [+8.0, +17.5] |
| gold sessions (budgeted ceiling) | 82.5 [83.8] | +11.5 [+6.8, +16.2] |
| all gold-session turns, uncapped (≈ 5.5K tokens) | 73.8 [76.2] | +2.8 [−2.0, +7.2] |
| hybrid ranking with non-gold turns removed | 75.2 [77.8] | +4.2 [+1.0, +7.5] |
| dense | 72.2 [74.0] | +1.2 [−2.5, +5.2] |
| **hybrid** | **71.0** [73.2] | — |
| BM25 | 67.8 [70.5] | −3.2 [−7.0, +0.5] |
| hybrid hits + ±1 neighbour turns | 64.5 [66.8] | −6.5 [−10.8, −2.2] |
| hybrid sessions expanded around hits | 42.5 [44.2] | −28.5 [−33.5, −23.5] |
| random turns | 8.5 [9.8] | −62.5 |
| no retrieval | 6.0 [6.2] | −65.0 |

- **The three reference retrievers are statistically indistinguishable at n = 400.**
- **The reader degrades with context even when every token is relevant.** Answer turns alone score 83.8; the
  full gold sessions uncapped score 73.8 (−8.8 [−12.5, −5.0] vs the capped gold bundle).
- **The gap to the ceiling (11–13 points) is a coverage gap.** On questions whose bundle holds every answer
  turn, retrieval bundles score the same as gold sessions. The whole significant gap comes from missing answer
  turns (hybrid: +4.0 points from missing turns, +5.9 from missing sessions).
- **Spending the budget on local context loses.** Neighbour turns cost −6.5 points and session expansion
  −28.5, because fewer distinct hits fit. Traversal-style expansion must buy coverage, not surrounding text.
- **By question type,** gold sessions beat hybrid by +19.8 [+8.5, +31.1] on multi-session and +15.0
  [+5.6, +24.3] on temporal questions, but by 0.0 on single-session-user. The headroom is in multi-evidence
  questions.
- **Judge robustness:** every conclusion holds under the Qwen3-32B labels.

### 3.5 Accuracy vs token budget (hybrid ranking, test)
| cap (tokens) | 256 | 512 | 1,024 | **2,048** | 4,096 | 8,192 |
|---|---|---|---|---|---|---|
| accuracy | 46.0 | 53.8 | 68.2 | **71.0** | 72.0 | 71.0 |
| session recall@20 | 75.9 | 80.9 | 90.2 | 94.3 | 96.9 | 97.8 |
| acc. when all gold sessions present | 66.7 | 71.7 | 78.8 | 77.5 | 76.9 | 71.8 |

- **Accuracy is flat from 1,024 tokens on** (1,024 vs 2,048: −2.8 [−6.8, +1.2]), while recall keeps rising.
- **With all evidence present, more tokens lower accuracy** (78.8 → 71.8): extra tokens act as distractors.
- **Per-question budget oracle (upper bound for a budget-adaptive planner, H1):** matching the fixed-2,048
  accuracy needs 479 tokens per question on average (−76.6%). A free oracle reaches 87.0%.

  Caution: the oracle picks the best of six noisy reader outcomes per question, and the reader flips on about
  17% of questions when only unrelated bundle content changes (§3.7). Treat these as loose upper bounds.

### 3.6 Freshness on real data: LongMemEval knowledge-update pairs
70 of the 78 knowledge-update questions give a natural pair of old evidence and new evidence.

| ranking | Freshness@5 | stale version in top 5 |
|---|---|---|
| BM25 | 0.529 | 0.843 |
| dense | 0.414 | 0.700 |
| hybrid | 0.529 | 0.800 |

- **Better recall is not fresher evidence.** Dense has the highest recall but ranks the outdated version
  first most often: users restate a changed fact in words less like the question.
- **A recency prior** (score × (1 + 0.5·recency)) lifts hybrid Freshness@5 from 0.529 to 0.829.
  - It costs 9 points of session recall@5 across all questions.
  - End to end it **loses** 4.5 [−8.2, −0.8] points overall and leaves knowledge-update accuracy unchanged
    (82.3 vs 82.3).
  - The reader already picks the newer version by date when both are in the bundle; the prior mainly pushes
    other needed evidence out of the budget.
  - Freshness interventions should be judged on stale-served answers and accuracy, not on Freshness@k alone.
- **Stale-served answers** (gpt-oss stale judge): 6–9% of knowledge-update questions for retrieval bundles,
  7% for gold sessions, and 17% with uncapped full sessions. It is a reader failure amplified by long context.
- **Explicit vs implicit updates are hard to label on real data.** A lexical heuristic marks 6/70 explicit and
  an LLM label 39/70, and both fail spot checks. The controlled comparison uses the synthetic data instead.

### 3.7 Freshness on the synthetic stream (reference BM25 / dense / hybrid; updates fed in time order)
Freshness@5, mean ± sd over 3 seeds:

| method | plain | hide explicitly-superseded | recency prior | both |
|---|---|---|---|---|
| BM25 (10K) | 0.170 ± 0.021 | 0.204 ± 0.029 | 0.398 ± 0.006 | 0.444 ± 0.009 |
| dense (10K) | 0.213 ± 0.021 | 0.289 ± 0.023 | 0.545 ± 0.023 | 0.587 ± 0.026 |
| hybrid (10K) | 0.160 ± 0.029 | 0.218 ± 0.041 | 0.602 ± 0.019 | 0.640 ± 0.021 |
| BM25 (100K) | 0.165 ± 0.034 | 0.200 ± 0.043 | 0.430 ± 0.022 | 0.466 ± 0.028 |
| BM25 (1M, seed 0) | 0.149 | 0.171 | 0.432 | 0.477 |

- **Pointer-based invalidation barely helps.** A `supersedes` pointer closes one note, while restatements of
  the old value and older implicit versions stay live.
- **A recency prior helps much more**, and helps implicit updates as much as explicit ones. Invalidation keyed
  on (entity, attribute) would catch what pointers miss.
- **Freshness is flat from 10K to 1M notes** for BM25: scale changes the cost, not the freshness.
- **The real-data "dense is less fresh" result does not replicate here.** The generator phrases old and new
  versions from the same templates, so it does not test paraphrased updates. Adding those is a natural
  generator extension.
- **Reader accuracy does not follow ranking freshness.** Pooled over three independent 10K / 50K / 100K worlds
  (n = 960), every variant is within noise of plain BM25 (hide-superseded −0.2 [−1.1, +0.8], equivalent at
  ±2 points). Stale-only answers stay at 1.6–3.8%.
- **The 8B reader flips on about 17% of questions** when roughly a third of the bundle's unrelated notes
  change. That is a noise floor for every end-to-end comparison.
- **The synthetic set is leak-free.** The reader scores 0/600 with an empty bundle (chance 1.75%) and 84.4%
  with the gold notes alone.

### 3.8 Version resolution: can the reader handle stale versions if retrieval returns both?
Synthetic questions whose fact changed. Each bundle holds the notes for the current value, every superseded
note, and 4 notes on the same entity's other attributes. One neutral chain-of-note prompt for all conditions;
exact scoring on invented values.

| condition | `synth_10k` (n = 160) correct / stale | `synth_10k_high` (n = 213) correct / stale |
|---|---|---|
| new value only (perfect filtering) | 91.9 / 0.0 | 88.3 / 0.0 |
| old + new, time order, dated (our wrapper) | **91.9** / 5.0 | **89.2** / 2.8 |
| old + new, shuffled, dated | 88.7 / 8.7 | 85.0 / 9.9 |
| old + new, shuffled, **no dates** | **54.4** / 40.6 | **51.6** / 44.1 |
| old value only (update missed) | 0.0 / **91.9** | 0.0 / **89.2** |

- **Timestamps, not filtering, let the reader resolve versions.** With dates, handing the reader both the old
  and new value matches perfect filtering. Without dates it is close to a coin flip, and over 40% of answers
  are stale.
- **A missed update is served confidently.** With only the old version, the reader answers with it about 90%
  of the time and rarely abstains.
- **Implicit supersessions carry the residual errors** (with dates: implicit 82.5% vs explicit 97.0%). The
  worst case is implicit corrections without dates (33% correct).
- **Design rule for refresh (H4):** guarantee the *latest* version is retrieved, with its timestamp.
  Excluding stale versions adds nothing once dates are shown.

### 3.9 Context dilution: the same gold evidence + D distractor tokens
Evidence = all gold-session turns. Distractors come from the same history:
- *hard* = simulated same-user sessions; *easy* = ShareGPT / UltraChat chats;
- *last* / *first* = distractors dated before / after the evidence (the reader renders chronologically).

Answerable n = 91 dev questions; unanswerable = all 30 abstention questions (diagnostic).

| condition | tokens | answerable accuracy | Δ vs evidence only [95% CI] | unanswerable correctly declined |
|---|---|---|---|---|
| evidence only | 5.8K | 72.5 | — | 22 / 30 |
| + 4K hard, evidence last | 9.8K | 70.3 | −2.2 [−13.2, +8.8] | 20 / 30 |
| + 4K hard, evidence first | 9.8K | 68.1 | −4.4 [−13.2, +4.4] | 20 / 30 |
| + 4K easy, evidence last | 9.8K | 71.4 | −1.1 [−9.9, +7.7] | 19 / 30 |
| + 16K hard, evidence last | 21.2K | 61.5 | **−11.0 [−19.8, −2.2]** | 19 / 30 |
| + 16K hard, evidence first | 21.2K | 70.3 | −2.2 [−11.0, +6.6] | 19 / 30 |
| + 16K easy, evidence last | 19.5K | 61.5 | **−11.0 [−20.9, −1.1]** | 19 / 30 |

- **The amount of distraction matters, not its type.** 4K extra tokens are nearly free; 16K cost about 11
  points when they precede the evidence.
- **Position matters at long context.** Evidence placed first is robust to the same 16K.
- **More context brings more invented answers** to unanswerable questions (directional; small n).
- **Implication for H1:** budget-capped retrieval, and packing the strongest evidence where the reader sees
  it, are well motivated.
- **Backend check:** llama.cpp Q8_0 (CPU) and vLLM bf16 (GPU) give the same verdict on 86–92% of items, and
  every accuracy difference has a CI spanning 0.

### 3.10 Full-history baselines and window scaling (dev, 100 questions)
| window (most recent turns first) | 2K | 4K | 8K | 16K | 24K |
|---|---|---|---|---|---|
| accuracy | 8.0 | 6.0 | 10.0 | 18.0 | 25.0 |
| questions with all gold sessions in the window (of 94) | 2 | 2 | 2 | 6 | 10 |
| questions with any gold turn in the window | 3 | 6 | 16 | 35 | 49 |

- **The full-history baseline is coverage-bound.** Even the most recent 24K tokens (about a quarter of a
  history) hold all the evidence for only 10 of 94 questions. Compare 80% for the 400-token gold bundle and
  10% for random turns. The project needs retrieval; a bigger recency window does not substitute for it.
- **Test set (400):** gold 83.8, random 8.5, fullhist 2K 8.5, fullhist 16K 20.2. With the 16K window the
  reader declines only 17 of 24 unanswerable questions (vs 24/24 at 2K): it answers from related facts in the
  window.

### 3.11 Judge reliability
- **On dev the two judges agree on 95.9% of 2,500 judgments** (κ = 0.918).
- **On author-adjudicated disagreements, gpt-oss-20b was right 18 of 21 times.** The non-thinking Qwen3-32B
  accepted ~10% of "information not available" answers and rejected terse correct ones ("3" vs "three
  doctors…"). gpt-oss-20b is therefore the official judge.
- **On all pinned runs** (12 runs × 500 answers) the judges agree on 97.5% (κ = 0.948).
  - Single-session-preference questions are the exception (82% agreement, κ = 0.60); conclusions are not drawn
    from them alone.
  - On test the judges move overall accuracy by 1.3–2.8 points.
- **Human spot check** (20 dev answers, seed 0): an LLM proposed provisional labels and the author reviewed
  and confirmed all 20. gpt-oss-20b agrees with these labels on 19/20 and Qwen3-32B on 18/20.
- **Failure taxonomy** (wrong dev answers of the retriever-free bundles; the rule-based tag matches a 30-answer
  hand-tagged sample 29/30):
  - full history 2K: almost all truncation (90/92);
  - random: missing evidence (87/90);
  - gold: reader errors (17/20);
  - full history 16K: truncation (60), partial evidence (16), plus a few judge, version and reader errors.

### 3.12 Statistical power for the ±2-point parity criterion (H1)
| pair (vs hybrid, test) | discordant questions | paired SD | MDE at 80% power | n for ±2-pt equivalence |
|---|---|---|---|---|
| BM25 | 14.2% | 0.377 | 5.3 pts | 1,362 |
| dense | 15.8% | 0.397 | 5.6 pts | 1,515 |
| gold sessions | 24.0% | 0.477 | 6.7 pts | 2,184 |

- **±2-point parity cannot be established on 400 LongMemEval_S test questions.** Two reasonable plans
  disagree on 14–16% of questions; equivalence needs ~1,400–1,500 questions.
- **Recommendation:** report H1 as "the 95% CI excludes a loss larger than X", with the MDE stated, and run
  the tight equivalence test on the synthetic workload. Pooling three synthetic worlds (n = 960) gives ±1
  point for low-discordance pairs.

### 3.13 LongMemEval_M (same 500 questions, ~10× longer histories)
- **Retrieval cost:** BM25 for all 500 histories runs in 3 minutes on 16 cores (p95 20 ms per query).
  Dense needs ~507K unique turns embedded.
- **M is about 10 points harder.** BM25 accuracy is 57.2% vs 67.8% on S (Δ −10.5 [−14.5, −6.5], paired over
  the same 400 test questions).
- **The accuracy loss is the evidence loss.** Recall falls by about the same amount (session recall@5 0.766
  vs 0.858).
- **M fits the budget,** because bundles stay at 2,048 tokens. It is a useful stress test for the planner.

### 3.14 LongMemEval-V2 Small, text-only
Setup:
- 422 text-only questions; per-domain BM25 over trajectory notes.
- The official system prompts, message layout and scorer, taken from the LongMemEval-V2 repository.
- gpt-oss-20b judges the LLM-checked question types; the reader is Qwen3-8B.

| memory budget | accuracy [95% CI] | answered UNKNOWN | static | dynamic | procedure | flawed premise |
|---|---|---|---|---|---|---|
| none (official no-retrieval baseline) | 2.4 [0.9, 3.8] | 73.7% | 4.5 | 0.0 | 5.4 | 0.0 |
| BM25, 2,048 tokens | 17.3 [13.7, 20.9] | 34.8% | 23.1 | 12.8 | 39.2 | 0–3.6 |
| BM25, 8,192 tokens | 20.6 [16.8, 24.6] | 19.9% | 29.1 | 15.1 | 40.5 | 0–7.3 |
| BM25, 24,576 tokens | 21.6 [17.8, 25.6] | 7.3% | 37.3 | 16.3 | 32.4 | 0–4.9 |

Memory query time is 0.36 s per question.
- **The pipeline transfers to agent-trajectory memory:** 2.4% → 17–22%.
- **Bigger budgets mostly turn "UNKNOWN" into wrong answers.** UNKNOWN falls from 35% to 7% while accuracy
  gains only ~4 points: extra context makes the reader commit, not know.
- **Workflow questions benefit most** (~40%). Flawed-premise questions stay near 0: an 8B reader rarely
  detects a false premise.
- These numbers are not comparable to the paper's leaderboard (different reader, BM25 instead of its memory
  modules, open judge, text only).

## 4. Summary of implications for the project
1. **Retrieval coverage, not context size, is what limits accuracy.** The gap to the gold ceiling comes
   entirely from missing answer turns, and full-history windows rarely contain the evidence.
2. **More tokens hurt an 8B reader once the evidence is in.** This holds for budget sweeps, uncapped gold
   sessions and added distractors. Budget-capped plans (H1) are justified, and a ~1,024-token budget loses
   little.
3. **Freshness:** retrieve the latest version with its timestamp. Dates let the reader resolve old versus
   new; ranking-level freshness priors cost recall without buying accuracy.
4. **Evaluation design:** report freshness at the evidence level and accuracy separately. Use the synthetic
   workload for tight equivalence tests, because LongMemEval_S cannot resolve ±2 points.
5. **Benchmark hygiene:** hash session ids, report judge agreement, and note that about half of each
   LongMemEval_S haystack is style-separable filler.
